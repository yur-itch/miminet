Разобрался, почему сбрасывается прогресс. Воспроизвёл на PostgreSQL.

**Механизм:**
1. Каждый клик «Начать» по разделу создаёт новую `QuizSession` (`quiz_session_facade.start_session`).
2. Перед этим фронт вызывает `PUT /quiz/session/finishold` (`quiz_scripts.js: finishOldQuiz()`), а `finish_old_sessions` ставит `finished_at = now()` **всем** незавершённым сессиям пользователя во всех разделах, в том числе брошенным без единого ответа.
3. Счётчик «N/M верно» берёт последнюю сессию по `finished_at DESC` (`quiz/util/dto.py`: `SectionDto` и `get_last_correct_question_count_by_section`).

Получается: задание 7 решено (1/1) → пользователь снова открыл задание 7 и не ответил → начал задание 8 → брошенная сессия задания 7 получает самый свежий `finished_at` → задание 7 показывает 0/1. Ровно как в issue.

Ещё деталь: в PostgreSQL при `DESC` значение NULL идёт первым, поэтому незавершённая сессия считается «последней» ещё до `finishold`. Но `nulls_last()` основную проблему не решает, я проверил.

Кроме того, `SectionDto` не фильтрует `is_deleted`, а `get_last_correct_question_count_by_section` фильтрует, то есть логика в двух местах расходится.

**Как лучше исправить?**
- **A.** Показывать лучший результат среди завершённых сессий («решено — значит решено»). Для практики, по-моему, это самое логичное, но для контрольных (`is_exam`), возможно, нужно иначе.
- **B.** Показывать последнюю сессию, в которой был хотя бы один ответ (пустые игнорировать).
- **C.** В `finish_old_sessions` не закрывать пустые сессии, а помечать удалёнными. Это меняет поведение для экзаменов, поэтому самый рискованный вариант.

В любом варианте сведу выбор сессии в одну функцию для обоих мест, добавлю `nulls_last()` и тест на PostgreSQL (в SQLite этот баг не воспроизводится). Какой вариант предпочтительнее?
